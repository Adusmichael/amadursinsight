Human-in-the-Loop Safeguard Protocol

Unvetted AI output introduces specific, nameable risks: hallucinated edge cases, missed non-functional requirements, unaddressed stakeholder conflicts, and no clear owner of accountability. This protocol describes the six mechanisms AmadursInsight uses to keep a human answerable for every requirement before it reaches a backlog — and names where those mechanisms currently fall short.

The six mechanisms

01

Forced, strict-schema output

Prevents free-text hallucination bleeding into the deliverable

The model is not asked to "write a BRD" — it is forced to call one tool (record_requirements) whose input must validate exactly against a fixed JSON schema (strict: true, tool_choice pinned to that one tool). There is no path for the model to return prose, markdown, or a field that doesn't fit the contract. Every requirement, story, and criterion that exists in the output exists because it filled a required, typed slot — not because the model decided to mention it.

02

Gaps become questions, not answers

Prevents invented detail, fabricated metrics, guessed acceptance thresholds

The extraction prompt is explicit: where the notes give no target ("make it faster"), record the ambiguity as an open question rather than supplying a number. The same rule governs assumptions and non-functional requirements — if the source material doesn't state it, the model is instructed to say so, not to fill the gap with something plausible. This is a hallucination reduction mechanism, not a hallucination detector — see Limitations.

03

Conflict detection, never auto-resolved

Prevents unaddressed stakeholder conflicts shipping silently into a sprint

An optional second input accepts an existing backlog or ticket export. The model checks it against the meeting notes — and against itself — for contradictions: two stakeholders wanting opposite behaviour, a ticket asking for something the notes rule out, two tickets that can't both be true. Each conflict is returned as its own artifact: description, the exact sides in involves, and a recommendation naming who to ask. The prompt forbids the model from picking a side. A conflict with no named resolver is dropped rather than guessed.

04

"First draft" framing, no auto-publish

Prevents a draft being mistaken for an approved spec, or shipped without a human touching it

Every generated document is labelled, in the UI itself, as a first draft to refine — not a finished specification. There is no "push to Jira" or "publish" action anywhere in the tool. The only way a document leaves is a human choosing Copy or Download, at which point responsibility for its content transfers explicitly to them.

05

Deterministic change-impact, not another model call

Prevents a human's correction being silently reinterpreted or overwritten by AI

Once a human edits a requirement, the app walks a plain in-memory graph (parent/child IDs captured at generation) and flags every downstream user story and acceptance criterion as review-needed. No model is called to do this. A human's edit cannot be quietly "smoothed over" by a second AI pass — the flag is mechanical and the review is manual.

06

Inspectable, versioned extraction logic

Prevents "the AI decided" as an unaccountable answer

The schema and system prompt that define what the model is allowed to return are plain text files in the project repository, not hidden configuration. For any submitted document, the exact extraction contract used to produce it can be pulled up, read, and reproduced. Governance change control applies to the prompt the same way it would to a policy document.

Who signs off on what

RoleReviewsBefore it may proceed
Junior BA Every requirement, story, and criterion line by line against the source notes Marks each item reviewed; corrects wording in place (the tool's own edit step)
Senior BA The Conflicts section specifically, plus a spot-check of Assumptions and Open Questions Confirms each conflict has been routed to the named resolver — not resolved by guesswork
BA Practice Lead The extraction prompt and schema themselves (governance, not individual documents) Owns what "reviewed" means org-wide; any prompt change goes through the same change control as a BRD template

Nothing produced by this prototype is treated as approved until a named human has signed off at the level above. The tool has no concept of "approved" — that status lives outside it, in whatever system of record the organisation already uses.

Named limitations

  • Mechanism 02 reduces invented detail by instruction; it is not an independent hallucination check. A second, differently-prompted model pass to cross-examine the first draft would be a stronger guarantee and is not yet built.
  • Conflict detection (03) only sees what is pasted into the backlog field. It does not connect live to Jira, so a conflicting ticket the reviewer forgets to paste in is invisible to it.
  • The protocol assumes the three sign-off roles above are staffed and distinct. In a team of one, the same person plays all three — which is workable, but removes the second-reviewer effect the table is designed to give.
  • Compliance record-keeping (who reviewed what, when) is a process today, not a logged feature of the tool. Formalising it as an audit trail is the natural next build.
